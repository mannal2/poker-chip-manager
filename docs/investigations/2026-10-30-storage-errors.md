# 간헐적 저장·불러오기 오류 조사 — 2026-10-30

## 1. 증상

- 사용자 보고: 리팩토링 배포본(`origin/main` 2f58ec1)을 갤럭시 **설치 앱(PWA)** 에서 쓰는 중 저장 오류와 불러오기 오류가 간헐적으로 발생했다.
- 오류 화면의 "새 토너먼트 시작"도 실패했다. 앱을 완전히 닫았다가 다시 열어도 한동안 오류가 계속됐다.
- 어떤 조작 뒤에 생겼는지, 화면에 어떤 문구가 떴는지는 기록이 없다. 조사 시점에는 정상으로 돌아와 문구를 확인할 수 없었다.
- 같은 기기의 설치 앱에서 2026-10-20에도 저장 무응답이 있었다([이전 조사](2026-10-20-storage-stall.md)). 그때도 기기 쪽 최초 원인은 확정하지 못했다.

## 2. 조사

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 리팩토링이 저장 경로를 바꿈 | 7190526~61ae556의 저장소·세션 변경 비교 | 저장소는 타입 위치 이동뿐, 세션은 파일 분리(`useCrossTabOwnership`·`usePageResume`·`commandRunner`)로 동작 동일. 확인창 `ask`도 `window.confirm` 그대로 → 원인 아님 |
| 엔진이 만든 정상 상태를 복원 검사(`validateStored`)가 거부 | 2~10인 무작위 게임 약 15만 7천 단계마다 `validateStored` 실행(임시 테스트, 미커밋) | 거부 0건 → 원인 아님 |
| 기기 저장소가 쓰기를 거부하면 읽기까지 실패 | 코드 확인 + 쓰기 거부 모사 테스트 | **확인됨.** `load()`가 읽기만 하는데도 `readwrite` 트랜잭션을 열어, 쓰기가 막히면 불러오기도 `QuotaExceededError`로 실패 |

"다시 열어도 안 됨"은 연결 일시 끊김보다 저장소 자체의 실패(저장 공간 부족에 따른 쓰기 거부, 브라우저 저장소 오류 등)와 맞는다. 하지만 실제 오류 종류를 보지 못했으므로 **최초 원인은 확정하지 않는다.**

## 3. 수정

1. **불러오기를 읽기 전용으로** (826f463): `LocalRepository.load()`를 `readonly` 트랜잭션으로 바꿨다. 쓰기가 막힌 기기에서도 저장된 게임과 조작권 기록은 읽힌다. 조작·새 토너먼트처럼 실제로 써야 하는 작업은 여전히 실패하며, 이는 앱이 해결할 수 없는 기기 상태다.
2. **오류 진단 기록**: 저장소 작업이 실패할 때마다 단계·오류 종류(`error.name`)·메시지·시각·화면 상태·설치 앱 여부를 `localStorage`(`poker-local:storage-errors`)에 최근 10건 남긴다. IndexedDB가 실패해도 남도록 IndexedDB 밖에 둔다. 복구 화면과 저장 오류 안내에 "오류 정보"(펼치기)와 "오류 정보 복사" 버튼을 표시한다.

## 4. 다음에 발생하면

오류 화면의 "오류 정보 복사"로 내용을 보내 주면 아래처럼 원인을 가린다.

| 기록된 오류 | 뜻 |
|---|---|
| `QuotaExceededError` | 기기 저장 공간 부족·저장 한도 초과 |
| `UnknownError` / `InvalidStateError` | 브라우저가 IndexedDB 연결을 끊었거나 저장소 오류 |
| `Error: 저장 상태를 확인하지 못했습니다 (…)` | 8초 동안 응답 없음 |
| `Error: 저장 … 손상되었습니다` | 저장 데이터 검사 실패 |

## 5. 검증

- 단위: 쓰기 거부 시 불러오기 테스트(RED: `QuotaExceededError` → GREEN), 오류 기록 3건. 전체 207 통과, 타입 검사·린트 통과.
- E2E(Chromium·WebKit): `tablet-recovery`(복구 화면의 "오류 정보" 표시 추가), `stalled-save`, `storage`, `app-flow` 46 통과.
- 실기기(갤럭시 설치 앱) 재현·확인은 하지 못했다.
