# E2E 테스트 실행 시간 74% 단축 — 18분에서 4.7분으로

- 프로젝트: 포커 칩 매니저 (React·TypeScript PWA, IndexedDB 로컬 저장)
- 테스트 도구: Playwright 1.64 (Chromium·WebKit 두 브라우저)
- 작업일: 2026-10-27
- 결과 요약: 전체 E2E 436개의 실행 시간 **1,077초 → 평균 281초** (약 3.8배 빠름), 3회 연속 전부 통과
- 후속 조치: 테스트가 늘어나도 효과와 안정성이 유지되도록 순차 실행 목록 자동 검사와 테스트 작성 규칙을 추가

---

## 1. 문제 인식

리팩토링을 작은 단위로 나눠 진행하면서, 단위마다 "검증 후 커밋"하는 규칙을 두었다.
그런데 E2E 전체 검사를 한 번 돌리는 데 **약 18분**이 걸렸다.

- 단위 작업 하나에 검증 대기만 18분이 붙었다. 하루에 여러 번 커밋하기 어려웠다.
- 시간을 아끼려고 "관련 spec만 골라 실행"하는 방식으로 바꿨다. 하지만 어떤 spec이 관련되는지 매번 사람이 판단해야 했고, 놓친 회귀는 마지막 전체 실행에서야 드러났다.
- 결국 **검증을 줄이는 쪽이 아니라 검증 자체를 빠르게 만드는 쪽**이 맞다고 판단했다.

## 2. 문제 원인 분석

### 2-1. 먼저 측정했다

처음 손에 있던 정보는 "총 18분"뿐이었다.
기존 실행은 `line` 리포터로 돌려서 테스트별 소요 시간이 남지 않았다.
어디가 느린지 모른 채 최적화 방법을 고르면 효과를 추측에 맡기게 된다.
그래서 같은 전체 검사를 **JSON 리포터로 한 번 더 실행해 테스트별 시간을 수집**했다.

| 항목             | 값                                                                               |
| ---------------- | -------------------------------------------------------------------------------- |
| 전체 실행 시간   | 1,077초 (테스트 436개, worker 1개)                                               |
| 테스트 시간 합계 | 1,058초 — 거의 전부가 테스트를 하나씩 순서대로 실행한 시간                       |
| 브라우저별       | **WebKit 787초 (74%)**, Chromium 271초                                           |
| 느린 파일 상위   | `game` 137초, `design` 130초, `interaction-revision` 129초, `tablet-layout` 95초 |
| 가장 느린 테스트 | 10인 리버 보드 배치 (WebKit) 23.2초                                              |

### 2-2. 측정에서 찾은 원인

1. **모든 테스트가 직렬 실행이었다.**
   설정이 `workers: 1`이라 CPU 18코어 중 1개만 썼다. 시간 대부분이 대기 시간이었다.
2. **WebKit이 Chromium보다 2~4배 느렸다.**
   같은 테스트라도 `board`는 4.1배, `game`은 3.8배 차이가 났다. 직렬 실행에서는 느린 쪽이 전체 시간을 그대로 늘린다.
3. **병렬화를 막는 공유 자원이 있었다.**
   `pwa`·`startup-update` 테스트는 업데이트 감지를 검증하려고 빌드 결과물 `dist/local/sw.js`를 직접 고쳤다가 되돌린다.
   그런데 앱은 모든 `/local/` 페이지에서 이 서비스 워커를 등록한다.
   다른 테스트가 동시에 돌면 고쳐진 `sw.js`를 보고 업데이트 안내를 띄울 수 있다.
   **worker 수만 올리면 테스트끼리 간섭할 수 있는 구조**였다.

### 2-3. 후보 방법을 데이터로 걸렀다

검토한 방법을 측정 결과에 비춰 하나씩 판단했다.

| 후보                             | 판단                 | 근거                                                                                                                   |
| -------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 테스트 병렬 실행                 | **채택 — 핵심**      | 직렬 대기가 시간 대부분이고 CPU 여유가 크다                                                                            |
| PWA 테스트 분리·순차 실행        | **채택 — 필수 조건** | 병렬화하려면 `sw.js` 공유 문제를 먼저 풀어야 한다                                                                      |
| 변경 범위별로 일부만 실행        | 보조 수단으로 유지   | Playwright `--only-changed`는 E2E 파일이 앱 소스를 import하지 않는 구조라 쓸 수 없었다                                 |
| 디자인 검사 스크린샷 줄이기      | 채택 (작은 정리)     | 성공할 때도 매번 264장을 저장했다. 판정은 CSS 값 비교로 하고 스크린샷은 진단용이다. 시간보다는 산출물 정리 효과가 크다 |
| 고정 대기(`waitForTimeout`) 제거 | 보류                 | 14곳 대부분이 "길게 누르기" 드래그에 실제로 필요한 입력 시간이고, 합쳐도 약 15초다                                     |
| preview 서버 미종료 조사         | 해당 없음            | 10회 넘게 실행한 뒤에도 포트 4173에 남은 서버가 없어 재현되지 않았다                                                   |

## 3. 해결 방법

### 3-1. 설정을 바꾸기 전에 실험했다

저장소 설정은 건드리지 않고, 임시 설정 파일로 `sw.js`를 고치는 spec 2개를 뺀 410개를 돌렸다.

| 실험                         | 시간  | 결과      | 관찰                                                                              |
| ---------------------------- | ----- | --------- | --------------------------------------------------------------------------------- |
| worker 4개                   | 314초 | 전부 통과 | 테스트 하나당 속도는 기준과 같았다                                                |
| worker 8개                   | 193초 | 전부 통과 | 테스트 하나당 16% 느려졌다. 가장 느린 테스트가 26.8초로 기본 제한 30초에 근접했다 |
| SW spec 2개를 따로 순차 실행 | 54초  | 전부 통과 | 분리해도 문제없이 동작했다                                                        |

### 3-2. worker를 6개로 정한 이유

미리 실험한 것은 4개와 8개 두 가지다.
6개는 이 두 결과 사이에서 판단으로 고른 값이고, 적용한 뒤 3회 실행으로 확인했다.

"테스트 하나당 느려짐"은 같은 테스트를 직렬로 실행했을 때보다 하나하나가 얼마나 오래 걸렸는지를 뜻한다.
worker끼리 CPU를 나눠 쓰면서 생기는 경합을 보여주는 지표다.

| worker 수 | 언제 측정       | 전체 시간               | 테스트 하나당 느려짐 | 가장 느린 일반 테스트 (제한 30초) |
| --------- | --------------- | ----------------------- | -------------------- | --------------------------------- |
| 1 (기준)  | 변경 전         | 1,077초                 | —                    | 23.2초                            |
| 4         | 사전 실험       | 314초 + SW 54초         | +1%                  | 24.2초                            |
| 8         | 사전 실험       | 193초 + SW 54초         | +16%                 | 26.8초                            |
| **6**     | **적용 후 3회** | **267~298초 (SW 포함)** | **+4% ~ +16%**       | **25.3~25.8초**                   |

사전 실험은 일반 테스트와 SW 테스트를 따로 실행해서 빌드를 두 번 했다. 적용 후 실행은 한 번에 돌려서 빌드를 한 번만 한다.

판단 근거는 네 가지다.

1. **4개에서 8개로 가면 효과가 점점 줄어든다.**
   worker를 2배로 늘렸지만 일반 단계 시간은 314초에서 193초로 1.6배만 빨라졌다.
   같은 구간에서 테스트 하나당 느려짐은 +1%에서 +16%로 커졌다.
   4개와 8개 사이 어딘가에서 CPU 경합이 본격적으로 시작된다는 뜻이다.
   특히 WebKit 테스트가 무거워서 동시에 많이 띄울수록 서로 느려진다.
2. **8개는 시간 제한 여유가 너무 적다.**
   가장 느린 테스트가 26.8초로, 기본 제한 30초까지 여유가 3.2초뿐이었다.
   테스트가 늘거나 다른 프로그램이 CPU를 쓰는 순간에는 이 여유가 사라진다.
   그러면 실제 버그가 없는데도 시간 초과로 실패하는 간헐적 실패가 생긴다.
3. **실행 환경의 부하가 일정하지 않다.**
   이 PC에는 다른 개발 도구의 프로세스도 함께 떠 있었다.
   실제로 6개로 3회 돌린 결과도 회차마다 +4%, +9%, +16%로 달랐다.
   3회차는 8개 실험과 같은 수준까지 느려졌다.
   같은 설정이라도 PC 상태에 따라 경합이 크게 흔들리므로, 최고 속도보다 여유를 남기는 쪽을 택했다.
4. **포기한 속도는 크지 않다.**
   8개로 한 번에 돌렸다면 약 227초로 추정된다(193초 + 54초에서 중복 빌드 약 20초를 뺀 값). 6개보다 회당 40~70초 빠른 셈이다.
   대신 간헐적 실패의 위험을 줄였다.
   간헐적 실패 한 번을 조사하는 데 드는 시간이 이 차이보다 훨씬 크다고 판단했다.

함께 둔 장치와 한계:

- 시간 제한에 가장 가까운 10인 리버 배치 테스트 3개에는 `test.slow()`를 따로 붙였다(3-4).
  worker 수를 줄이는 것과 별개로, 이 테스트들의 제한 시간 자체를 90초로 늘렸다.
- CI는 4코어 러너라 worker를 2개로 따로 정했다.
- 5개와 7개는 실험하지 않았다. 그래서 6개가 측정으로 찾은 최적값이라고 말할 수는 없다.
  PC 사양이 바뀌거나 테스트가 크게 늘면 `npx playwright test --workers=N`으로 간단히 다시 비교할 수 있다.

### 3-3. 실행을 두 단계로 나눴다

```ts
// playwright.config.ts (요약)
const serviceWorkerSpecs = ['**/pwa.spec.ts', '**/startup-update.spec.ts'];

export default defineConfig({
  workers: process.env.CI ? 2 : 6, // GitHub 기본 러너는 4코어
  projects: [
    // 1단계: 일반 테스트 — 두 브라우저 병렬
    { name: 'chromium', testIgnore: serviceWorkerSpecs, ... },
    { name: 'webkit', testIgnore: serviceWorkerSpecs, ... },
    // 2단계: sw.js를 고치는 테스트 — 1단계 뒤에 하나씩
    { name: 'chromium-sw', testMatch: serviceWorkerSpecs,
      dependencies: ['chromium', 'webkit'], workers: 1, ... },
    { name: 'webkit-sw', testMatch: serviceWorkerSpecs,
      dependencies: ['chromium-sw'], workers: 1, ... },
  ],
});
```

설계하면서 짚은 점:

- **SW 단계는 순서를 사슬로 묶었다.**
  처음에는 브라우저별 SW project에 `workers: 1`만 줬다.
  하지만 이 값은 project 안에서만 제한이라, `chromium-sw`와 `webkit-sw`가 서로 동시에 돌 수 있었다.
  그러면 두 브라우저가 같은 `sw.js`를 동시에 고치게 된다.
  그래서 `webkit-sw`가 `chromium-sw`를 기다리도록 의존 관계를 이었다.
- **사용법은 바꾸지 않았다.**
  `npm run test:e2e` 한 줄로 두 단계가 순서대로 돌고, 빌드와 preview 서버도 한 번만 시작한다.
  CI처럼 파일을 지정해 실행하는 방식도 그대로 쓸 수 있다고 봤지만, CI에서 직접 확인하지 않았고 실제로는 틀렸다(5-5 참고).
- **알려진 제약을 문서에 남겼다.**
  1단계에서 실패가 나면 의존 관계 때문에 2단계는 건너뛴다.
  순서를 보장하는 대가이며, 아키텍처 문서의 검증 절에 적어 두었다.

### 3-4. 병렬 환경에 맞춘 보정

- 화면을 실제로 눌러 30번의 행동을 저장하며 리버까지 진행하는 테스트 3개에 `test.slow()`를 붙였다.
  병렬 부하에서도 시간 제한에 여유가 생긴다.
  상태를 저장소에 바로 넣어 시작하면 더 빨라지지만, 그러면 테스트가 확인하는 범위가 달라져서 하지 않았다.
- 디자인 비교 테스트는 스타일 비교가 실패할 때만 승인 화면과 실제 화면의 스크린샷을 저장하게 바꿨다.
  검증 조건 자체는 그대로다.

## 4. 효과

### 4-1. 실행 시간

바꾼 설정으로 전체 E2E를 **3회 연속** 실행했다.
병렬화 뒤에 생길 수 있는 간헐적 실패를 확인하려는 목적이다.

| 회차           | 시간    | 결과               | 가장 느린 테스트 |
| -------------- | ------- | ------------------ | ---------------- |
| 기준 (변경 전) | 1,077초 | 434 통과, 2 건너뜀 | 23.2초           |
| 1회            | 267초   | 434 통과, 2 건너뜀 | 25.3초           |
| 2회            | 277초   | 434 통과, 2 건너뜀 | 25.7초           |
| 3회            | 298초   | 434 통과, 2 건너뜀 | 25.8초           |

- 평균 **281초(4.7분), 기준 대비 74% 단축**
- 3회 모두 실패·불안정 0건. 건너뛴 2개는 원래 Chromium에서만 도는 터치 테스트다.
- 3회 모두 SW 단계가 정해진 순서(`chromium-sw` → `webkit-sw`)로, 일반 단계가 끝난 뒤 실행된 것을 기록으로 확인했다.
- 디자인 검사가 성공할 때 남기던 스크린샷 264장이 0장이 됐다.

### 4-2. 작업 방식의 변화

- 작은 작업은 관련 spec만, 넓은 범위의 변경은 매번 전체 E2E를 돌리는 방식으로 바꿨다. 전체 검사 한 번이 5분 안에 끝나서 단위 작업마다 돌릴 수 있게 됐다.
- "어떤 spec이 관련 있나"를 사람이 고르다 회귀를 놓칠 위험이 줄었다.

## 5. 후속 조치 — 테스트가 늘어나도 유지되도록

설정을 바꾼 것으로 끝내지 않았다.
앞으로 기능을 추가하면 E2E 테스트도 계속 늘어난다.
그때 이번 개선이 조용히 무너질 수 있는 지점을 먼저 찾고, 각각 막는 장치를 두었다.

### 5-1. 예상한 리스크

| 리스크                                                         | 일어나면 생기는 일                                                                                                                             |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 새 spec이 공유 파일을 고치는데 순차 실행 목록에 넣는 걸 잊는다 | 다른 테스트와 동시에 돌면서 **가끔만** 실패한다. 매번 실패하지 않아서 원인을 찾기 가장 어려운 종류의 버그가 된다                               |
| 목록 이름이 `serviceWorkerSpecs`라 서비스 워커 전용처럼 보인다 | 다른 공유 상태를 고치는 테스트가 생겨도 목록에 넣어야 한다고 생각하지 못한다                                                                   |
| 기존의 큰 spec 파일에 테스트를 계속 덧붙인다                   | worker는 파일 단위로 일을 받는다. 그래서 파일 하나가 길어지면 다른 worker가 일찍 끝나도 그 파일이 전체 시간을 결정하고, 병렬화 효과가 줄어든다 |
| 반대로 안전하게 하려고 아무 테스트나 순차 목록에 넣는다        | 순차 단계가 길어져 다시 느려진다                                                                                                               |

### 5-2. 리스크별 조치

**① 목록 누락은 사람이 기억하는 대신 테스트가 잡게 했다.**

- 순차 실행 목록을 설정 파일에서 분리해 `e2e/sharedStateSpecs.ts` 한 곳에서 관리하게 했다.
- Vitest 가드 테스트를 추가했다.
  - E2E spec 중 `dist/`에 파일을 쓰는 코드가 있으면, 그 파일이 목록에 있는지 확인한다.
  - 빠져 있으면 "○○를 e2e/sharedStateSpecs.ts에 추가하세요"라는 메시지로 실패한다.
  - 목록에는 있는데 실제 파일이 없는 경우도 실패한다. 파일 이름을 바꾼 뒤 목록이 낡아 보호가 사라지는 경우를 막는다.
- 가드가 실제로 동작하는지 확인했다. 목록에서 `pwa.spec.ts`를 일부러 빼자 위 메시지로 실패했다.
- E2E보다 먼저, 수 초 안에 끝나는 단위 테스트 단계에서 실패하게 했다. 그래서 누락은 커밋 전 검사에서 바로 드러난다.

**② 이름이 의도를 말하게 했다.**

- `serviceWorkerSpecs`를 `sharedStateSpecs`로 바꿨다.
- 순차 단계 project 이름도 `chromium-sw`·`webkit-sw`에서 `chromium-serial`·`webkit-serial`로 바꿨다.
- 기준이 "서비스 워커냐"가 아니라 "모든 테스트가 같이 쓰는 걸 바꾸느냐"라는 게 이름에서 드러난다.

**③ 파일 비대화는 규칙과 기준값으로 막았다.**

- 아키텍처 문서의 테스트 절에 작성 규칙을 추가했다. 새 기능의 테스트는 기존 큰 파일에 덧붙이지 않고 기능별 spec 파일로 만든다.
- 규칙만 적지 않고 이유와 기준값을 함께 남겼다.
  - 이유: 파일 단위로 나눠 실행하기 때문에 한 파일이 병목이 된다.
  - 기준값: 지금 가장 긴 파일은 약 110초이고, 전체를 worker 6개에 고르게 나누면 약 176초다. 그래서 아직 병목은 없다.
  - 나중에 이 숫자와 비교해 병목이 생겼는지 판단할 수 있다.
- 병목이 생겼을 때의 대응도 정해 두었다. 그 파일의 테스트가 서로 독립적이면 그 파일에만 파일 안 병렬 실행을 켠다. 전체 설정을 바꾸지 않아서 다른 테스트에 영향이 없다.

**④ 과잉 격리도 막았다.**

- 순차 목록에 넣지 않아도 되는 것을 문서에 명시했다. IndexedDB·서비스 워커 등록·BroadcastChannel은 Playwright가 테스트마다 새 브라우저 컨텍스트를 만들어 이미 격리한다.
- 불안해서 목록에 넣는 일이 생기지 않게 해, 순차 단계가 불필요하게 길어지는 것을 막는다.

### 5-3. 남은 한계

- 가드 테스트가 자동으로 찾는 것은 `dist/`에 쓰는 코드뿐이다.
- preview 서버처럼 다른 공유 상태에 영향을 주는 테스트는 아직 문서 규칙과 코드 리뷰에 의존한다.
- 그런 테스트가 실제로 생기면 가드의 검사 조건을 넓히는 것이 다음 단계다.

### 5-4. 검증

- 단위 테스트 187개 통과 (가드 테스트 2개 포함)
- E2E 전체 434개 통과, 274초
- 실행 기록으로 순서를 확인했다. 순차 단계가 일반 단계가 끝난 뒤 시작했고, `chromium-serial` → `webkit-serial` 순서로 돌았다.

### 5-5. CI에서 드러난 빈틈

브랜치를 PR로 올리자 CI의 브라우저 테스트가 실패했다.

- **증상**: CI는 원래 `app-flow`·`game`·`pwa` 세 파일만 지정해 60개를 돌린다. 그런데 이번에는 440개를 돌렸고, 그중 디자인 테스트 36개가 실패했다.
- **원인**: 순차 단계(`chromium-serial`)는 일반 단계 project가 끝나야 시작하도록 의존 관계로 묶여 있다. Playwright는 의존 대상 project를 돌릴 때 명령줄의 파일 지정을 적용하지 않고 그 project의 테스트를 전부 돌린다. `pwa.spec.ts`가 순차 단계에 있어서, 이 파일 하나를 지정하면 전체가 따라왔다. 로컬에서 `--list`로 재현했다(세 파일 지정 시 440개, `pwa` 제외 시 48개).
- **디자인 테스트가 실패한 이유**: 이 테스트는 그동안 CI(리눅스)에서 한 번도 돈 적이 없었다. 리눅스 기본 글꼴은 폭이 넓어서 320·360px 화면에서 좌석 숫자가 칸을 넘친다. main 코드에서도 똑같이 실패하는 것을 확인했다. 즉 원래 있던 문제가 이번 일로 드러났다. 이 문제는 별도 작업으로 다룬다.
- **조치**: CI 명령에 `--no-deps --workers=1`을 붙였다. 의존 project를 끌어오지 않으니 지정한 세 파일만 돌고, worker 1개라 두 브라우저의 `pwa.spec.ts`가 겹치지 않는다. 로컬에서 같은 명령으로 62개가 모두 통과했다.

## 6. 배운 점

- **측정 없이 최적화하지 않는다.**
  총 시간만 보면 "디자인 스크린샷이 무겁다", "고정 대기가 많다" 같은 그럴듯한 가설이 먼저 떠오른다.
  실제로 재 보니 고정 대기는 다 합쳐 약 15초였다.
  디자인 검사도 파일 전체가 130초(12%)라, 스크린샷만 줄여서는 효과에 한계가 있었다.
  대부분의 시간은 직렬 실행과 WebKit에서 나왔다.
- **병렬화의 핵심은 worker 수가 아니라 공유 자원이다.**
  숫자를 올리기 전에 테스트끼리 같이 쓰는 것(여기서는 디스크의 `sw.js`)을 찾고 격리해야 한다.
  격리 방식에도 빈틈이 있었다. project별 worker 제한만으로는 project끼리 동시에 도는 걸 막지 못했다.
- **빠른 쪽보다 안정적인 쪽을 고른다.**
  worker 8개가 더 빨랐지만 시간 제한 여유가 3초밖에 없었다.
  6개를 택하고, 바꾼 뒤 여러 번 연속으로 돌려 간헐적 실패가 없는지 확인한 뒤에 확정했다.
- **개선은 유지 장치까지 만들어야 끝난다.**
  설정을 바꾼 직후에는 누구나 규칙을 기억하지만, 몇 달 뒤 새 테스트를 쓰는 사람은 모를 수 있다.
  잊기 쉬운 규칙은 테스트로 강제하고, 강제하기 어려운 규칙은 이유와 기준값을 함께 문서로 남겼다.
- **"확인하지 않았다"고 적은 곳은 실제로 확인해야 한다.**
  CI 동작을 확인하지 않았다고 문서에 써 두었는데, 바로 그 지점이 문제가 됐다.
  실행 설정을 바꾸면 로컬 전체 실행뿐 아니라 CI가 쓰는 명령도 `--list`로 확인해야 한다.
