# 바이인(추가 참가·재입장) 설계

## 목적

토너먼트가 진행 중일 때 새 플레이어가 들어오거나, 탈락한 플레이어가 다시 사서 들어올 수 있게 한다. 실제 대회의 늦은 등록과 재입장(re-entry)에 해당한다. 단일기기 모드에 먼저 넣어 규칙을 확인하고, 그다음 멀티플레이에 넣는다.

## 근거가 되는 정식 규칙

Poker TDA 규칙(2015년판 7번, 2019년판 8번, 최신판 9번)은 늦게 등록한 사람과 재입장한 사람을 똑같이 다룬다. 이들은 시작 칩 전액을 받고, 아무 자리에나 앉으며, 바로 카드를 받는다. 단 **스몰 블라인드와 버튼 사이 자리**에 앉으면 버튼이 지나갈 때까지 기다린다. 리바이(자리를 유지한 채 칩만 사기)와 애드온은 다른 방식이므로 이번 범위에 넣지 않는다.

## 목표

- 진행 중인 토너먼트에 **새 플레이어 추가**와 **탈락자 재입장**을 같은 "바이인" 기능으로 제공한다.
- 바이인한 사람은 **시작 칩 전액**을 받는다.
- **자리는 바이인을 넣는 사람이 고른다.** 단일기기에서는 운영자, 멀티플레이에서는 승인하는 방장이다.
- 두 엔진(TypeScript, Java)이 같은 결과를 내도록 규칙을 **공용 게임 픽스처**(`shared/game-fixtures`)로 고정한다.

## 비목표

- 리바이, 애드온, 바이인 금액 입력, 상금·참가비 계산
- 늦은 등록 마감 시점 설정. 단일기기는 제한이 없고, 멀티플레이는 방장 승인으로 통제한다.
- 토너먼트가 끝난 뒤의 바이인

## 결정 사항 (사용자 확정 2026-11-19)

1. **칩**: 시작 칩(`settings.initial`) 전액으로 고정한다. 토너먼트 칩 총량(`initialTotal`)도 그만큼 늘린다.
2. **참여 시점**
   - 바이인은 핸드 진행 중에도 받는다. 카드는 **다음 핸드부터** 받는다.
   - 다음 핸드에서 앉은 자리가 버튼과 스몰 블라인드 사이(시계 방향, 양 끝 제외)라면 **버튼이 그 자리를 지나갈 때까지 대기**한다.
3. **탈락자 재입장 자리**: 자리 고르기에서 **원래 자리를 기본 선택**으로 두고, 다른 자리로 바꿀 수 있다.
4. **10명 정원과 빈자리**: 탈락자의 빈자리도 좌석 수에 들어간다. 새 사람은 **탈락자의 빈자리를 차지**할 수 있다. 자리가 10개이고 빈자리가 없으면 바이인할 수 없다.
5. **종료 뒤**: 토너먼트가 끝나면(`ended`·`aborted`) 바이인을 받지 않는다. 다만 아직 자리에 앉지 않은 바이인이 있으면, 남은 사람이 1명이어도 토너먼트를 끝내지 않는다.
6. **취소**: 바이인한 사람이 **첫 카드를 받기 전까지만** 취소할 수 있다. 취소하면 그 사람이 차지했던 탈락자 빈자리는 원래대로 돌아간다. 첫 카드를 받은 뒤에는 취소할 수 없다(멀티플레이는 기존 기권 처리를 쓴다).
7. **표시와 기록**
   - 재입장한 사람의 카드에 재입장 횟수를 작게 표시한다(예: `×2`).
   - 기록에 바이인과 재입장을 남긴다.
8. **단일기기 진입점**: 메뉴 버튼(☰)을 누르면 뜨는 메뉴에 `바이인` 버튼을 넣는다.
9. **멀티플레이**
   - 진행 중인 방에 새로 들어오면, 지금의 "이미 게임이 시작된 방입니다" 거절 대신 "게임이 진행 중입니다. 바이인을 신청할까요?"로 바이인 신청을 보낸다.
   - 탈락자는 방 화면의 `다시 참가(바이인)` 버튼으로 신청한다.
   - 방장은 복구 신청과 같은 알림·대화상자에서 승인하거나 거절하고, **승인할 때 자리를 정한다.**

## 방식 비교

- **A. 바이인 = 새 참가 기록 (선택)**: 바이인할 때마다 새 플레이어 기록(새 id)을 만든다. 탈락자 빈자리를 차지하면 그 탈락자 기록은 자리에서 빠지지만, 이름은 기록용 명단에 남긴다. 재입장은 같은 이름에 참가 횟수를 하나 더한 새 기록이다. TDA가 재입장을 "새 참가"로 보는 것과 같다. 기존 기록의 의미(그 기록이 무엇을 했는지)가 바뀌지 않는다.
- B. 재입장은 같은 기록 되살리기: 탈락 표시를 지우고 칩을 다시 준다. 원래 자리일 때는 간단하다. 하지만 다른 자리로 옮기거나 빈자리를 차지할 때 좌석 이동 처리가 필요하고, 과거 기록의 "탈락"과 현재 상태가 충돌한다.
- C. 좌석 배열 대신 별도 대기열만 두기: 다음 핸드 시작 때 한꺼번에 반영한다. 반영 전에는 단순하다. 하지만 좌석 위치·버튼 대기 규칙을 결국 좌석 배열에서 다시 풀어야 해서 복잡도가 줄지 않는다.

A를 고른다. 재입장과 새 플레이어가 같은 처리를 공유하고, 과거 기록이 그대로 유지된다.

## 상태와 규칙

### 플레이어 기록에 더할 값

- `entry`: 이 사람의 몇 번째 참가인지(1부터). 새 사람은 1이고, 재입장은 직전 기록의 `entry + 1`이다.
- `joining`: 아직 첫 카드를 받지 않은 바이인 상태. 값은 다음 둘 중 하나다.
  - `'next-hand'`: 다음 핸드 시작을 기다림
  - `'button'`: 버튼이 지나가기를 기다림
  
  첫 카드를 받으면 값을 지운다. `joining`인 사람은 베팅 차례, 블라인드, 팟 자격에 들어가지 않는다.
- `replaced`: 이 바이인이 차지한 탈락자 기록. 취소할 때 되돌리는 데 쓰고, 첫 카드를 받으면 지운다.

### 토너먼트 상태에 더할 값

- `formerPlayers`: 자리에서 빠진 탈락자 기록의 `{ id, name }` 목록. 기록 화면이 과거 이벤트의 이름을 찾을 수 있게 한다. 지금 기록 화면은 현재 플레이어 목록에서 이름을 찾으므로([history.ts:40](../../../frontend/src/features/gameplay/model/history.ts)), 이 목록도 함께 찾게 바꾼다.

### 명령

- `BUY_IN { name, placement, reentryOf? }`
  - `placement`: `{ kind: 'between', after: playerId }` 또는 `{ kind: 'replace', playerId }`. `between`은 그 사람 바로 다음(시계 방향)에 새 자리를 만들고, `replace`는 탈락자 빈자리를 차지한다.
  - `reentryOf`: 재입장일 때 탈락한 기록의 id. 이름과 `entry`를 거기서 이어받는다.
  - 거절 조건
    - 토너먼트가 `playing`이 아님
    - 이름 규칙 위반, 또는 지금 앉아 있는(탈락하지 않았거나 `joining`인) 사람과 이름이 겹침(대소문자 무시)
    - 자리가 10개인데 `between`을 고름
    - `replace` 대상이 탈락자가 아님
    - `reentryOf`가 탈락자가 아님
    - 같은 탈락 기록으로 이미 진행 중인 재입장이 있음
- `CANCEL_BUY_IN { playerId }`: `joining`인 사람만 대상이다. 그 자리를 없애거나 `replaced`를 되돌리고, `initialTotal`에서 시작 칩만큼 뺀다.
- 새 플레이어 id는 지금 플레이어와 `formerPlayers` 어느 쪽과도 겹치지 않아야 한다(지금 id는 `p0`, `p1`… 형태다).
- 재입장할 이름을 다른 사람이 이미 쓰고 있으면(그 사이 새 사람이 같은 이름으로 들어온 경우) 이름 중복으로 거절한다. 재입장은 이름을 바꾸지 않는다(설계자 판단).
- 칩 불변식: `initialTotal`은 바이인마다 시작 칩만큼 늘고 취소하면 줄어든다. 차지한 탈락자 기록은 칩이 0이므로 합계에 영향이 없다. `joining`인 사람은 `pending`·`actorId`에 들어가지 않으므로 기존 차례 검사와 충돌하지 않는다.
- 두 명령 모두 **취소(UNDO) 스냅샷을 비운다.** 바이인 뒤에 이전 행동을 되돌리면 바이인이 함께 사라지기 때문이다. 화면은 "바이인 뒤에는 이전 행동을 취소할 수 없습니다."를 안내한다.

### 좌석 번호가 바뀔 때

`between`으로 자리를 만들면 그 뒤 좌석 번호가 하나씩 밀린다. 진행 중인 핸드의 `buttonSeat`, `sbSeat`, `bbSeat`와 `undo` 스냅샷의 좌석 번호도 같이 옮겨야 한다. undo는 위 규칙대로 비우므로 핸드 좌석 번호만 옮기면 된다. `setupOrder`가 있으면 그것도 맞춘다.

### 다음 핸드 시작 때의 순서

1. `joining: 'next-hand'`인 사람을 모두 `'button'` 후보로 바꾼다.
2. `joining`인 사람을 뺀 생존자로 다음 핸드의 버튼·블라인드를 기존 `nextPositions`로 계산한다.
3. 대기자 자리가 그 버튼과 스몰 블라인드 사이(시계 방향, 양 끝 제외)에 있으면 `'button'`으로 계속 대기한다. 아니면 이번 핸드부터 참여시킨다(`joining` 해제).
4. 참여시킨 사람이 있으면, 그 사람들을 포함한 생존자로 위치를 다시 계산한다. 2명에서 3명이 되는 경우도 이 계산이 맡는다.

### 토너먼트 종료 판정

핸드가 끝날 때 "생존자 1명이면 종료"에서, `joining`인 사람도 생존자로 센다.

## 화면

### 단일기기

- 메뉴(☰)의 `바이인`을 누르면 대화상자가 열린다.
  - **누가**: `새 플레이어`(이름 입력) 또는 탈락자 목록에서 고르기(재입장)
  - **어디에**: 좌석 목록에서 고른다. "A와 B 사이" 또는 "C의 빈자리(탈락)" 형태다. 재입장이면 원래 자리를 미리 고른다.
  - **안내**: "시작 칩 1,000을 받고 다음 핸드부터 참여합니다." 버튼 대기에 걸릴 자리라면 "버튼이 지나간 뒤 참여합니다."
- 토너먼트가 진행 중이 아니거나 자리가 없으면 버튼은 흐리게 보이고, 누르면 이유를 보여 준다(기존 `aria-disabled` 방식).
- `joining`인 사람의 카드에는 "다음 핸드부터" 또는 "버튼 대기"를 표시한다. 그 카드를 누르면 `바이인 취소`를 고를 수 있다.
- 재입장한 사람의 카드 이름 옆에 `×2`처럼 표시한다.
- 기록 문구: "Bob 바이인", "Bob 재입장(2번째)", "Bob 바이인 취소". 합니다체 문장 규칙과 맞춘다.

### 멀티플레이 (2단계)

- 서버에 바이인 신청 목록을 둔다. 복구 신청과 같은 모양이지만 별도 목록이다.
  - 유효 시간 5분
  - 방장이 바뀌거나 사라질 때의 처리
  - 요청 남발 제한
- 화면
  - 방장: [HostRequests.tsx](../../../frontend/src/features/online-game/components/HostRequests.tsx)에서 복구 신청과 바이인 신청을 함께 보여 준다. 바이인 승인 대화상자에 단일기기와 같은 자리 고르기를 넣는다.
  - 신청자: 복구 신청과 같은 "방장의 승인을 기다리고 있습니다" 화면과 결과 확인 흐름을 쓴다.
- 서버는 승인할 때 Java 엔진에 `BUY_IN`을 실행한다.
  - 새 사람이면 참가자 자리를 만들고 자격을 발급한다.
  - 재입장이면 기존 참가자를 새 플레이어 기록에 다시 연결한다.
- Java 엔진은 1단계에서 만든 공용 픽스처를 그대로 통과해야 한다.

## 단계

1. **단일기기**
   - TypeScript 엔진에 `BUY_IN`·`CANCEL_BUY_IN`과 다음 핸드 시작 규칙을 넣는다.
   - 공용 픽스처에 바이인 사례를 추가한다.
   - 단일기기 메뉴·대화상자·카드 표시·기록을 만든다.
2. **멀티플레이**
   - Java 엔진에 같은 규칙을 넣는다(공용 픽스처 통과).
   - 서버에 바이인 신청·승인 흐름을 만든다.
   - 입장 화면·방 화면·방장 알림을 연결한다.

1단계를 실기기에서 확인한 뒤 2단계를 시작한다.

## 구현자에게 맡기는 부분

- 자리 고르기 화면의 배치(목록인지 테이블 위 선택인지). 기존 좌석 카드와 대화상자 스타일을 따른다.
- `formerPlayers`를 상태에 둘지, 기록 이벤트에 이름을 함께 남길지. 기록 화면이 이름을 잃지 않는다는 조건만 지키면 된다.
- 엔진 내부의 좌석 번호 이동을 어떤 함수로 묶을지.
