# PWA 적용 범위 재설계와 진입점 분리 — 오프라인 앱과 실시간 멀티플레이를 한 사이트에서

- 프로젝트: 포커 칩 매니저 (React·TypeScript, Vite, vite-plugin-pwa)
- 작업일: 2026-10-27
- 결과 요약
  - 멀티플레이도 설치한 앱 안에서 쓰도록 하되, **서비스 워커는 단일 기기 모드에만** 두는 구조로 결정했다(방안 C′).
  - 세 페이지가 하나의 번들을 함께 받던 구조를 **진입점 3개로 분리**했다. 온라인 페이지가 받는 JS는 306KB에서 220KB로 줄었고, 로컬 저장소·PWA 코드가 빠졌다.
  - 서비스 워커가 미리 저장하는 파일 목록이 **로컬이 실제로 쓰는 파일과 정확히 같은지** 자동으로 검사한다.

---

## 1. 문제 인식

이 앱은 두 가지 모드를 한 사이트에서 제공한다.

| 모드                    | 성격                                             | 필요한 것                                                              |
| ----------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| 단일 기기 (`/local/`)   | 한 기기에서 칩 계산, 데이터는 기기 안(IndexedDB) | 인터넷 없이 열리고, 게임 도중에는 업데이트로 화면이 바뀌지 않아야 한다 |
| 멀티플레이 (`/online/`) | 서버와 실시간 통신                               | 항상 서버와 같은 버전이어야 한다                                       |

처음 기획(T53)은 "PWA는 단일 기기만, 멀티플레이는 일반 웹"이었다.
리팩토링 감사에서 이 의도와 실제 빌드 결과가 다르다는 점을 발견했다.

```
dist/assets/main-….js   306 KB   ← 루트·로컬·온라인 세 HTML이 모두 이 파일 하나를 받음
```

- **온라인 페이지가 필요 없는 코드를 받았다.** 지금은 "준비 중" 안내뿐인데도 IndexedDB 저장소·게임 화면·PWA 등록 코드까지 306KB를 통째로 받았다.
- **로컬 서비스 워커의 저장 규칙이 너무 넓었다.** 규칙이 `assets/**/*.{js,css}`, 즉 "자산 폴더 전부"였다. 멀티플레이 코드가 생기면 그 파일도 로컬 앱의 오프라인 캐시에 들어간다.
- **스타일 적용이 우연에 기대고 있었다.** 전역 스타일은 로컬 화면만 import했고, 온라인 페이지는 번들이 하나라서 우연히 스타일을 받고 있었다.
- **루트(`/`)와 `/online/` 경로에 대한 테스트가 하나도 없었다.**

## 2. 결정 과정 — "멀티플레이에도 PWA를 쓰면 편하지 않을까?"

진입점을 나누는 계획을 세우던 중, 이 질문이 나왔다. 질문에 답하려면 PWA가 무엇으로 이뤄져 있는지부터 나눠 봐야 했다.

### 2-1. PWA를 기능 단위로 나눴다

| 기능                                  | 담당               | 단일 기기 | 멀티플레이                     |
| ------------------------------------- | ------------------ | --------- | ------------------------------ |
| 설치 (홈 화면 아이콘, 주소창 없는 창) | manifest           | 유용      | **유용**                       |
| 오프라인 실행                         | 서비스 워커 + 캐시 | 핵심      | 무의미 (서버 없이는 게임 불가) |
| 업데이트 대기 (홈에서 사용자가 적용)  | 서비스 워커        | 필요      | **위험**                       |

"PWA를 쓸지 말지"는 하나의 질문이 아니었다. 기능마다 답이 달랐다.

### 2-2. 멀티플레이에서 서비스 워커가 위험한 이유

서비스 워커는 앱 파일을 저장해 두었다가 그 저장본으로 화면을 연다.

- 단일 기기는 앱과 데이터가 모두 기기 안에 있다. 옛 버전을 조금 더 써도 문제가 없다.
- 멀티플레이는 서버와 같은 요청 형식으로 대화해야 한다. 서버가 새 버전으로 바뀌었는데 저장된 옛 화면 코드가 계속 뜨면, 옛 형식의 요청을 보내 거절되거나 오작동한다.

즉 멀티플레이는 "항상 최신"이어야 하고, 단일 기기는 "천천히 업데이트"여야 한다. 두 요구가 정반대다.

### 2-3. 대안 비교

| 방안                                  | 내용                                          | 판단                                                                                                                         |
| ------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| A. 현행 유지                          | 설치·서비스 워커 모두 `/local/`만             | 설치한 앱에서 멀티플레이로 가면 "앱 범위 밖"이 되어 주소창이나 브라우저 화면이 겹쳐 보인다                                   |
| B. 앱 전체를 하나의 서비스 워커로     | 한 워커가 사이트 전체를 제어                  | 한 워커 안에서 "천천히"와 "항상 최신"을 섞어 관리해야 한다. 이미 검증한 오프라인·업데이트 동작을 처음부터 다시 검증해야 한다 |
| C. 온라인 전용 manifest 추가          | 멀티플레이는 서비스 워커 없이 따로 설치       | 위험은 피하지만 홈 화면 아이콘이 두 개가 된다                                                                                |
| **C′. manifest 범위만 사이트 전체로** | 설치 범위는 `/`, 서비스 워커 범위는 `/local/` | **채택**                                                                                                                     |

C′는 C를 검토하다가 나왔다.
"설치한 앱에서 멀티플레이를 누르면 어떻게 되나?"를 따져 보던 중, **manifest의 범위와 서비스 워커의 범위는 서로 독립적으로 정할 수 있다**는 점이 해결의 열쇠가 됐다.

| 항목                      | 값             | 효과                                                                                   |
| ------------------------- | -------------- | -------------------------------------------------------------------------------------- |
| manifest `scope`          | `/`            | 설치한 앱 창 안에서 멀티플레이도 주소창 없이 열린다                                    |
| manifest `start_url`·`id` | `/local/` 유지 | 아이콘을 누르면 오프라인에서도 앱 홈이 열린다. 이미 설치한 앱의 식별자가 바뀌지 않는다 |
| 서비스 워커 범위·캐시     | `/local/` 유지 | 멀티플레이는 캐시 없이 매번 서버의 최신 파일을 받는다                                  |

설치 편의는 두 모드가 함께 얻고, 멀티플레이의 "옛 화면이 새 서버와 대화하는" 위험은 구조적으로 생기지 않는다.

### 2-4. 따라오는 질문들을 하나씩 확인했다

- **"설치 안내는 사이트의 첫 페이지에서 띄우면?"**
  - 실제로 확인해 보니 루트 `/`는 화면 없이 곧바로 `/local/`로 이동한다. 사용자가 처음 보는 화면은 이미 앱 홈이고, 설치 안내도 이미 거기 있었다.
  - 루트를 진짜 첫 화면으로 만들면 서비스 워커 범위 밖이라 오프라인에서 열리지 않는다. 그래서 설치 안내는 앱 홈 한 곳으로 정했다.
- **"두 모드가 같이 쓰는 파일이 옛날 버전이면?"**
  - 빌드 파일 이름에는 내용의 해시가 붙는다. 내용이 바뀌면 이름도 바뀌므로 "이름은 같은데 내용은 옛것"인 경우가 없다.
  - 옛 버전이 남을 수 있는 곳은 HTML과 `sw.js`뿐이다. 그래서 이 둘은 오래 캐시하지 않는다는 원칙을 기록했다.
- **"멀티플레이에서 새 파일을 받으면 로컬 캐시도 갱신되나?"**
  - 아니다. 브라우저 기본 캐시와 서비스 워커 캐시는 서로 독립적이다.
  - 로컬 캐시는 자기 업데이트 절차(새 `sw.js` 감지 → 대기 → 사용자 적용)로만 바뀐다.
  - 두 모드의 버전이 잠시 달라질 수 있지만 서로 다른 페이지라 코드를 섞어 쓰지 않으므로 안전하다.

결정과 대안, 적용 시점은 기술 결정 문서(T53 갱신)와 시스템 명세에 기록했다.
manifest 범위 변경과 실기기 확인은 멀티플레이 화면을 만들 때 적용한다. 지금은 "준비 중" 화면뿐이라 설치해도 쓸 게 없기 때문이다.

## 3. 해결 방법 — 진입점 분리 (E 묶음)

어느 방안을 고르든 "온라인 파일은 로컬 캐시에 넣지 않는다"는 조건은 같다. 그래서 진입점 분리는 결정과 별개로 바로 진행했다.

### 3-1. HTML마다 자기 진입점

| HTML                | 진입점            | 내용                           |
| ------------------- | ----------------- | ------------------------------ |
| `local/index.html`  | `main.local.tsx`  | 로컬 게임 화면 (PWA 등록 포함) |
| `online/index.html` | `main.online.tsx` | 준비 중 안내                   |
| `index.html`        | `main.home.tsx`   | `/local/`로 이동               |

- 공통 시작 처리(확대 정책 설치, React 루트 생성)는 `mount()` 하나로 모았다.
- 주소를 보고 화면을 고르던 `App` 컴포넌트는 지웠다.

### 3-2. 파일 이름으로 캐시 범위를 표현

- 빌드 파일 이름이 진입점 이름으로 시작하게 했다: `local-…`, `online-…`, `home-…`
- 공통 파일에는 읽을 수 있는 이름을 붙였다: React는 `react-…`, 시작 코드는 `start-…`
- 나중에 온라인 전용 코드가 별도 파일로 쪼개져도 `online-`이 붙도록 규칙을 두었다. 판단 기준은 그 파일의 모듈이 모두 `features/online-game/` 아래에 있는지다.
- 서비스 워커의 저장 대상에서 `home-*`·`online-*`를 제외했다.

### 3-3. 이름 규칙을 믿지 않고 결과를 검사

이름 규칙은 사람이 지키는 약속이라 언젠가 어긋날 수 있다. 그래서 **빌드 결과물 자체**를 검사하는 테스트를 만들었다.

1. 로컬 HTML이 링크하는 파일에서 출발한다.
2. 각 JS 파일이 import하는 파일을 끝까지 따라가, 로컬이 실제로 닿는 파일 목록을 구한다. 화면에서 나중에 불러오는 업데이트 도우미(`workbox-window`)도 여기에 포함된다.
3. 서비스 워커의 저장 목록과 **정확히 같은지** 비교한다.
   - 빠진 파일이 있으면 오프라인에서 앱이 깨진다.
   - 남는 파일이 있으면 온라인·루트 파일이 섞인 것이다.

같은 spec에서 경로 동작도 확인한다. 이전에는 테스트가 없던 부분이다.

- `/`에 들어가면 `/local/`로 이동한다.
- 로컬에서 서비스 워커를 설치한 뒤 `/online/`으로 가도, 온라인 페이지는 서비스 워커 제어를 받지 않는다.
- `/online/`은 로컬 전용 파일을 하나도 요청하지 않는다.

### 3-4. 전역 스타일 분리

- `tokens.css`에는 `:root` 변수만 남기고, 나머지 전역 규칙은 **순서를 그대로 유지한 채** `base.css`로 옮겼다.
- 세 진입점이 모두 이 두 파일을 같은 순서로 import한다. 온라인 페이지가 우연히 스타일을 받던 상태가 해소됐다.
- 게임 헤더 스타일처럼 위치를 옮기면 규칙 순서가 바뀌는 부분은 별도의 스타일 작업으로 남겼다.

## 4. 효과

### 4-1. 페이지별로 받는 파일

| 페이지 | 변경 전 JS | 변경 후 JS       | 로컬 저장소·PWA 코드 |
| ------ | ---------- | ---------------- | -------------------- |
| 온라인 | 306,328 B  | 220,331 B (−28%) | 포함 → **없음**      |
| 루트   | 306,328 B  | 220,299 B (−28%) | 포함 → **없음**      |
| 로컬   | 306,328 B  | 305,833 B        | 그대로               |

- 온라인 페이지는 CSS도 로컬 게임 스타일 없이 전역 스타일(4.4KB)만 받는다. 전에는 15KB였다.
- 줄어든 폭이 28%에 그친 이유는 남은 크기의 대부분이 React(219KB, 압축 시 약 68KB)이기 때문이다. 화면이 있는 페이지라면 피할 수 없는 크기다.

### 4-2. 캐시 목록

- 서비스 워커 저장 목록이 로컬 진입점이 실제로 쓰는 파일 6개로 정확히 맞춰졌다.
- 일부러 제외 규칙을 지워 보자 검사가 `online-…js`, `home-…js`가 섞였다고 정확히 지목하며 실패했다. 검사가 실제로 동작함을 확인했다.

### 4-3. 검증

- 단위 테스트 197개 통과
- E2E 전체 443개 통과 (진입점 분리 후, CSS 분리 후 각각 실행). 새 경로·캐시 검사 포함
- CSS 분리 후 빌드된 공통 스타일 파일의 내용 해시가 분리 전과 같았다. 사용자가 받는 CSS가 한 바이트도 바뀌지 않았다는 증거다.

## 5. 리스크를 줄이려고 신경 쓴 점

| 리스크                                                   | 대응                                                                                                                 |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 캐시 목록에서 로컬 파일이 빠져 오프라인에서 앱이 깨짐    | 이름 규칙이 아니라 빌드 결과물의 실제 의존 관계로 검사. 일부러 규칙을 깨서 검사가 잡는지 확인                        |
| 나중에 생길 온라인 전용 파일이 로컬 캐시에 섞임          | 온라인 모듈로만 된 파일에 자동으로 `online-`이 붙는 규칙. 그래도 어긋나면 위 검사가 잡음                             |
| CSS를 옮기면서 화면 모양이 바뀜                          | 규칙 순서를 유지한 채 잘라 옮기고, 원본과 이어 붙인 결과가 같은지 확인. 빌드 결과 해시로 동일성 재확인               |
| 파일 이름이 내용을 잘못 설명해 유지보수 때 혼동          | React 묶음이 `tokens-…`, 업데이트 도우미가 `shared-…`로 잘못 불리는 것을 발견해 `react-`·`start-`·원래 이름으로 정리 |
| Windows 경로(`\`)에서 이름 규칙이 어긋남                 | 모듈 경로를 `/`로 바꾼 뒤 비교. 포매터가 정규식을 바꿔 놓은 부분도 직접 문자열 처리로 교체                           |
| manifest 범위 변경으로 기존 설치 앱이 다른 앱으로 인식됨 | `id`와 `start_url`은 그대로 두기로 결정에 명시                                                                       |
| 결정이 대화 속에만 남음                                  | 대안·선택 이유·적용 시점을 기술 결정 문서(T53)와 시스템 명세에 기록                                                  |

## 6. 남은 한계와 다음 단계

- **공통 파일(React)을 두 모드가 각각 한 번씩 받을 수 있다.** 서버가 해시가 붙은 `/assets/` 파일에 "오래 저장해도 됨(`immutable`)" 헤더를 주면 해결된다. 배포 설정 변경이라 별도 작업으로 남겼다.
- **manifest 범위 변경(C′)은 아직 적용하지 않았다.** 멀티플레이 화면을 만들 때 적용하고 Android·iOS 실기기에서 확인한다.
- **온라인 전용 파일 이름 규칙은 아직 실제로 쓰인 적이 없다.** 온라인 모듈이 아직 없기 때문이다. 대신 캐시 목록 검사가 결과를 직접 확인하므로, 규칙이 어긋나도 테스트가 잡는다.

## 7. 배운 점

- **기술 이름이 아니라 기능 단위로 나눠 생각한다.**
  "PWA를 쓸까?"는 답하기 어려운 질문이었다. "설치·오프라인·업데이트 대기를 각각 쓸까?"로 나누자 기능마다 답이 분명해졌다.
- **질문이 더 나은 설계를 찾게 한다.**
  "설치한 앱에서 멀티플레이를 누르면 어떻게 되나?"를 따라가다가, 두 범위를 따로 정할 수 있다는 점을 발견했다. 그 결과 처음 권했던 안(C)보다 나은 안(C′)을 찾았다.
- **설정을 믿지 말고 결과물을 검사한다.**
  캐시 범위를 이름 규칙으로 정했지만, 최종 확인은 빌드된 파일의 실제 의존 관계로 했다. 실제로 이름 규칙을 만들던 중에 잘못 붙은 파일 이름을 두 번 발견했다.
- **"안 바뀌었다"도 증거로 보여준다.**
  CSS 분리는 사용자가 보는 결과가 같아야 하는 작업이었다. 테스트 통과뿐 아니라 빌드 결과의 내용 해시가 같다는 것으로 동일성을 증명했다.
