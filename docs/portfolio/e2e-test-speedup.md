# E2E 테스트 실행 시간 74% 단축 — 18분에서 4.7분으로

- 프로젝트: 포커 칩 매니저 (React·TypeScript PWA, IndexedDB 로컬 저장)
- 테스트 도구: Playwright 1.64 (Chromium·WebKit 두 브라우저)
- 작업일: 2026-10-27
- 결과 요약: 전체 E2E 436개의 실행 시간 **1,077초 → 평균 281초** (약 3.8배 빠름), 3회 연속 전부 통과

---

## 1. 문제 인식

리팩토링을 작은 단위로 나눠 진행하면서, 단위마다 "검증 후 커밋"하는 규칙을 두었다.
그런데 E2E 전체 검사를 한 번 돌리는 데 **약 18분**이 걸렸다.

- 단위 작업 하나에 검증 대기만 18분이 붙었다. 하루에 여러 번 커밋하기 어려웠다.
- 시간을 아끼려고 "관련 spec만 골라 실행"하는 방식으로 바꿨다. 하지만 어떤 spec이 관련되는지 매번 사람이 판단해야 했고, 놓친 회귀는 마지막 전체 실행에서야 드러났다.
- 결국 **검증을 줄이는 쪽이 아니라 검증 자체를 빠르게 만드는 쪽**이 맞다고 판단했다.

## 2. 문제 원인 분석

### 2-1. 먼저 측정했다

처음 손에 있던 정보는 "총 18분"뿐이었다.
기존 실행은 `line` 리포터로 돌려서 테스트별 소요 시간이 남지 않았다.
어디가 느린지 모른 채 최적화 방법을 고르면 효과를 추측에 맡기게 된다.
그래서 같은 전체 검사를 **JSON 리포터로 한 번 더 실행해 테스트별 시간을 수집**했다.

| 항목             | 값                                                                               |
| ---------------- | -------------------------------------------------------------------------------- |
| 전체 실행 시간   | 1,077초 (테스트 436개, worker 1개)                                               |
| 테스트 시간 합계 | 1,058초 — 거의 전부가 테스트를 하나씩 순서대로 실행한 시간                       |
| 브라우저별       | **WebKit 787초 (74%)**, Chromium 271초                                           |
| 느린 파일 상위   | `game` 137초, `design` 130초, `interaction-revision` 129초, `tablet-layout` 95초 |
| 가장 느린 테스트 | 10인 리버 보드 배치 (WebKit) 23.2초                                              |

### 2-2. 측정에서 찾은 원인

1. **모든 테스트가 직렬 실행이었다.**
   설정이 `workers: 1`이라 CPU 18코어 중 1개만 썼다. 시간 대부분이 대기 시간이었다.
2. **WebKit이 Chromium보다 2~4배 느렸다.**
   같은 테스트라도 `board`는 4.1배, `game`은 3.8배 차이가 났다. 직렬 실행에서는 느린 쪽이 전체 시간을 그대로 늘린다.
3. **병렬화를 막는 공유 자원이 있었다.**
   `pwa`·`startup-update` 테스트는 업데이트 감지를 검증하려고 빌드 결과물 `dist/local/sw.js`를 직접 고쳤다가 되돌린다.
   그런데 앱은 모든 `/local/` 페이지에서 이 서비스 워커를 등록한다.
   다른 테스트가 동시에 돌면 고쳐진 `sw.js`를 보고 업데이트 안내를 띄울 수 있다.
   **worker 수만 올리면 테스트끼리 간섭할 수 있는 구조**였다.

### 2-3. 후보 방법을 데이터로 걸렀다

검토한 방법을 측정 결과에 비춰 하나씩 판단했다.

| 후보                             | 판단                 | 근거                                                                                                                   |
| -------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 테스트 병렬 실행                 | **채택 — 핵심**      | 직렬 대기가 시간 대부분이고 CPU 여유가 크다                                                                            |
| PWA 테스트 분리·순차 실행        | **채택 — 필수 조건** | 병렬화하려면 `sw.js` 공유 문제를 먼저 풀어야 한다                                                                      |
| 변경 범위별로 일부만 실행        | 보조 수단으로 유지   | Playwright `--only-changed`는 E2E 파일이 앱 소스를 import하지 않는 구조라 쓸 수 없었다                                 |
| 디자인 검사 스크린샷 줄이기      | 채택 (작은 정리)     | 성공할 때도 매번 264장을 저장했다. 판정은 CSS 값 비교로 하고 스크린샷은 진단용이다. 시간보다는 산출물 정리 효과가 크다 |
| 고정 대기(`waitForTimeout`) 제거 | 보류                 | 14곳 대부분이 "길게 누르기" 드래그에 실제로 필요한 입력 시간이고, 합쳐도 약 15초다                                     |
| preview 서버 미종료 조사         | 해당 없음            | 10회 넘게 실행한 뒤에도 포트 4173에 남은 서버가 없어 재현되지 않았다                                                   |

## 3. 해결 방법

### 3-1. 설정을 바꾸기 전에 실험했다

저장소 설정은 건드리지 않고, 임시 설정 파일로 `sw.js`를 고치는 spec 2개를 뺀 410개를 돌렸다.

| 실험                         | 시간  | 결과      | 관찰                                                                              |
| ---------------------------- | ----- | --------- | --------------------------------------------------------------------------------- |
| worker 4개                   | 314초 | 전부 통과 | 테스트 하나당 속도는 기준과 같았다                                                |
| worker 8개                   | 193초 | 전부 통과 | 테스트 하나당 16% 느려졌다. 가장 느린 테스트가 26.8초로 기본 제한 30초에 근접했다 |
| SW spec 2개를 따로 순차 실행 | 54초  | 전부 통과 | 분리해도 문제없이 동작했다                                                        |

이 실험으로 **worker 6개**를 골랐다.
8개는 더 빠르지만, 부하가 몰리면 느린 테스트가 시간 제한에 걸려 간헐적으로 실패할 위험이 있었다.

### 3-2. 실행을 두 단계로 나눴다

```ts
// playwright.config.ts (요약)
const serviceWorkerSpecs = ['**/pwa.spec.ts', '**/startup-update.spec.ts'];

export default defineConfig({
  workers: process.env.CI ? 2 : 6, // GitHub 기본 러너는 4코어
  projects: [
    // 1단계: 일반 테스트 — 두 브라우저 병렬
    { name: 'chromium', testIgnore: serviceWorkerSpecs, ... },
    { name: 'webkit', testIgnore: serviceWorkerSpecs, ... },
    // 2단계: sw.js를 고치는 테스트 — 1단계 뒤에 하나씩
    { name: 'chromium-sw', testMatch: serviceWorkerSpecs,
      dependencies: ['chromium', 'webkit'], workers: 1, ... },
    { name: 'webkit-sw', testMatch: serviceWorkerSpecs,
      dependencies: ['chromium-sw'], workers: 1, ... },
  ],
});
```

설계하면서 짚은 점:

- **SW 단계는 순서를 사슬로 묶었다.**
  처음에는 브라우저별 SW project에 `workers: 1`만 줬다.
  하지만 이 값은 project 안에서만 제한이라, `chromium-sw`와 `webkit-sw`가 서로 동시에 돌 수 있었다.
  그러면 두 브라우저가 같은 `sw.js`를 동시에 고치게 된다.
  그래서 `webkit-sw`가 `chromium-sw`를 기다리도록 의존 관계를 이었다.
- **사용법은 바꾸지 않았다.**
  `npm run test:e2e` 한 줄로 두 단계가 순서대로 돌고, 빌드와 preview 서버도 한 번만 시작한다.
  CI처럼 파일을 지정해 실행하는 방식도 설정상 그대로 쓸 수 있다(CI에서 직접 실행해 확인하지는 않았다).
- **알려진 제약을 문서에 남겼다.**
  1단계에서 실패가 나면 의존 관계 때문에 2단계는 건너뛴다.
  순서를 보장하는 대가이며, 아키텍처 문서의 검증 절에 적어 두었다.

### 3-3. 병렬 환경에 맞춘 보정

- 화면을 실제로 눌러 30번의 행동을 저장하며 리버까지 진행하는 테스트 3개에 `test.slow()`를 붙였다.
  병렬 부하에서도 시간 제한에 여유가 생긴다.
  상태를 저장소에 바로 넣어 시작하면 더 빨라지지만, 그러면 테스트가 확인하는 범위가 달라져서 하지 않았다.
- 디자인 비교 테스트는 스타일 비교가 실패할 때만 승인 화면과 실제 화면의 스크린샷을 저장하게 바꿨다.
  검증 조건 자체는 그대로다.

## 4. 효과

### 4-1. 실행 시간

바꾼 설정으로 전체 E2E를 **3회 연속** 실행했다.
병렬화 뒤에 생길 수 있는 간헐적 실패를 확인하려는 목적이다.

| 회차           | 시간    | 결과               | 가장 느린 테스트 |
| -------------- | ------- | ------------------ | ---------------- |
| 기준 (변경 전) | 1,077초 | 434 통과, 2 건너뜀 | 23.2초           |
| 1회            | 267초   | 434 통과, 2 건너뜀 | 25.3초           |
| 2회            | 277초   | 434 통과, 2 건너뜀 | 25.7초           |
| 3회            | 298초   | 434 통과, 2 건너뜀 | 25.8초           |

- 평균 **281초(4.7분), 기준 대비 74% 단축**
- 3회 모두 실패·불안정 0건. 건너뛴 2개는 원래 Chromium에서만 도는 터치 테스트다.
- 3회 모두 SW 단계가 정해진 순서(`chromium-sw` → `webkit-sw`)로, 일반 단계가 끝난 뒤 실행된 것을 기록으로 확인했다.
- 디자인 검사가 성공할 때 남기던 스크린샷 264장이 0장이 됐다.

### 4-2. 작업 방식의 변화

- 작은 작업은 관련 spec만, 넓은 범위의 변경은 매번 전체 E2E를 돌리는 방식으로 바꿨다. 전체 검사 한 번이 5분 안에 끝나서 단위 작업마다 돌릴 수 있게 됐다.
- "어떤 spec이 관련 있나"를 사람이 고르다 회귀를 놓칠 위험이 줄었다.

## 5. 배운 점

- **측정 없이 최적화하지 않는다.**
  총 시간만 보면 "디자인 스크린샷이 무겁다", "고정 대기가 많다" 같은 그럴듯한 가설이 먼저 떠오른다.
  실제로 재 보니 고정 대기는 다 합쳐 약 15초였다.
  디자인 검사도 파일 전체가 130초(12%)라, 스크린샷만 줄여서는 효과에 한계가 있었다.
  대부분의 시간은 직렬 실행과 WebKit에서 나왔다.
- **병렬화의 핵심은 worker 수가 아니라 공유 자원이다.**
  숫자를 올리기 전에 테스트끼리 같이 쓰는 것(여기서는 디스크의 `sw.js`)을 찾고 격리해야 한다.
  격리 방식에도 빈틈이 있었다. project별 worker 제한만으로는 project끼리 동시에 도는 걸 막지 못했다.
- **빠른 쪽보다 안정적인 쪽을 고른다.**
  worker 8개가 더 빨랐지만 시간 제한 여유가 3초밖에 없었다.
  6개를 택하고, 바꾼 뒤 여러 번 연속으로 돌려 간헐적 실패가 없는지 확인한 뒤에 확정했다.
